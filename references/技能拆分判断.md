# 技能拆分判断

把访谈里每件"反复做的工作"逐条过一遍下面的判断，得出一个归宿。

## 五个问题

| 问题 | 是 | 否 |
|---|---|---|
| A. 一个月会做 2 次以上吗？ | 继续 | 多半不做，或者只写一条规则 |
| B. 有固定做法吗（步骤、判断标准、格式）？ | 倾向做成技能 | 倾向轻量指令，或者先不做 |
| C. 需要专门知识或历史数据才能做好吗？ | 技能，并且要配知识库或状态文件 | 轻量指令可能就够 |
| D. 会产出要保存的东西吗？ | 要写清存哪里、什么时候算定稿 | — |
| E. 做错了代价大吗？ | 技能里要有检查步骤，或者要求用户确认 | — |

## 归宿

| 归宿 | 条件 | 放哪 |
|---|---|---|
| 技能 | A 是，并且 B 或 C 是 | `.agents/skills/<id>/` |
| 已有技能的一个新用法 | 和某个已有技能读同一批文件、服务同一个目的，只是输入或输出不同 | 已有技能里的二级路由表加一行 |
| 轻量指令 | A 是，但 B、C 都否，一步就能做完 | 入口文件"不用技能的几件事" |
| 一条规则 | 不是一件"工作"，而是所有工作都要守的约束 | 入口文件的规则边界或输出原则 |
| 不做 | A 否，并且做错代价也不大 | 蓝图的"这次不做"里写一句 |

## 粒度

- **按用户的意图拆，不按步骤拆。** "判断值不值得做""事前预测""事后复盘"如果读的是同一批数据，就是一个技能的三种用法，不是三个技能。
- **两个技能总是一起读同一份知识**：把知识抽成一个知识库型技能，两个技能都从它读。
- **一个技能的 `SKILL.md` 超过 250 行**：先试着把细节挪进 `references/`，挪完还是太长，再考虑拆。
- **拆完检查一遍**：每个技能都能用一句话说清"它让用户得到什么"。说不清的，说明拆得不对。

## 四种技能类型

| 类型 | 核心是什么 | 例子（中性领域） |
|---|---|---|
| 建档 | 采集服务对象的信息，生成和更新档案 | 新客户建卡、新项目立项 |
| 流程型 | 一套固定步骤，产出一个结果 | 审一份文件、做一次预测、写一份周报 |
| 知识库型 | 管一批积累下来的知识，按任务决定读哪几份 | 某人的写作风格、条款库、过往决策库 |
| 工具型 | 包装一个外部接口或命令，说清怎么调、调完怎么用 | 查公开数据、调一个第三方服务 |

一个工作台里，建档一般只有一个；流程型最多；知识库型往往被流程型引用；工具型要配合 `边界与安全.md`。

## 命名

- `id`：小写英文加连字符，说清"做什么"，比如 `contract-review`。不要用 `helper`、`assistant` 这种看不出用途的词。
- 中文名：2–6 个字，用户平时怎么叫就怎么叫。
- `description`：中文名 + 一句话说做什么 + 用户的原话触发语 + 和相邻技能的分界（"写开头走 X""不用于 Y"）。agent 是靠它决定加载哪个技能的，所以触发语要写用户真实会说的话。
