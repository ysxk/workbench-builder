# 技能写法

## 目录

```
<id>/
├── SKILL.md         ← 必需。分流、流程、读哪些、写哪些
├── references/      ← 方法、判断标准、格式说明（相对稳定，人写的）
├── knowledge/       ← 积累的知识（会增长，由指定的技能写入）
├── types/           ← 按类别分的写法，配 _新分类模板.md
└── assets/          ← 模板、素材、示例产物
```

只建用得到的子目录。

## frontmatter

```yaml
---
name: <id>
description: <中文名>。<一句话说做什么>。用于"<用户原话 1>""<用户原话 2>"……。<和相邻技能的分界>。
---
```

- agent 靠 `description` 决定要不要加载这个技能，所以触发语要写用户真实会说的话，越具体越好。
- 有多种用法的，在 description 里就把用法分出来，写清每种对应什么说法、会不会写文件。
- 写明分界：容易混淆的请求该交给谁（"写开头走 X"），哪些情况不用这个技能（"不用于 Y"）。

## 正文结构（流程型）

1. **标题 + 一两句话**：这个技能的依据是什么、最核心的判断是什么。
2. **先读这些**：一张表，写文件 → 干什么用 → 是不是每次都读。
3. **用法分流**（多用法时）：用户说什么 → 哪种用法 → 写不写文件。再写一句"说不清是哪种时怎么办"。
4. **每种用法的步骤**：编号写。每一步说清做什么、依据什么、产出什么。
5. **输出格式**：用代码块给一个**填好的示例**，不要只给空模板。AI 照着示例写比照着说明写准得多。
6. **存哪里**：文件路径、命名规则、写完能不能改。
7. **谁能写**（技能管着知识库或状态文件时）：每个文件由谁写、什么时候写。
8. **不要**：最容易犯的 3–6 个错。
9. **维护记录**（可选）：日期 + 改了什么 + 依据。

## 知识库型

`SKILL.md` 只管"这次读哪几份"：

1. 知识库文件表：文件 → 里面是什么。
2. 任务路由表：任务 → 按顺序读哪些 → 读完怎么做。
3. 知识库还没生成时怎么办（跳过哪些文件，并提示用户怎么生成）。
4. 谁能写这个知识库：每个文件的写入方和写入时机。

## 工具型

1. 什么时候用、什么时候不用（尤其要写明它拿到的数据**不能**冒充什么）。
2. 前置条件：密钥或登录怎么配。**只写去哪里配，不在技能里放密钥。**
3. 怎么找到对的接口或命令，怎么调用，调用失败了怎么办（停下并报告，不静默换通道）。
4. 拿到结果后存哪里、怎么标数据来源。
5. 配合 `边界与安全.md` 写操作边界。

## 技能里写什么、不写什么

技能是给 AI 的抽象指导，让它能解决**这一类**任务，不只是眼前这一个。

- **写**：理念（在优化什么、警惕什么）、方法（步骤、判断标准、取舍规则）、输出格式、常见失败。每条规则写成"在什么情况下 → 做什么 → 为什么 → 什么时候不适用"。
- **不写**：某个用户的数据、作品、偏好、案例；课程或资料里的原句、讲的人的数字。前者放知识库、档案或状态文件，技能里只写"去哪读、读不到怎么办"；后者见 `资料提炼.md`。
- **示例**：输出格式需要填好的示例时，用虚构的或中性的内容，并标"示意"。不要拿当前用户的真实内容当示例，否则 AI 会把示例当成模板照抄。
- **换人测试**：把技能交给另一个用户，`SKILL.md` 和 `references/` 应该一个字都不用改。

## 写作规矩

- `SKILL.md` 在 50–250 行之间。长了就把细节挪进 `references/`。
- 用祈使句和具体条件："用户只有一句话 → 按 X 做"，不写"可以考虑……"。
- 给阈值的要写依据。阈值只是暂定的，写明"暂定，复盘后调整"。
- 引用路径写全，从工作台根目录算起。
- 外部方法论写出处和许可证，并写明按本领域改了哪些。
- 不要在技能里重复写入口文件已有的规则，写一句"按 AGENTS.md 的 X"就够了。
