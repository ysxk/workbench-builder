# 架构模式

文件即系统的工作台常用 14 种结构。每种都按同一个格式写：**防什么事 → 什么时候要 → 什么时候不要 → 最小做法 → 常见坏法**。

用法：新建时逐条问"这个领域要不要它"；体检时逐条看"它有没有、有没有坏"；揣摩别的工作台时用这些名字对号入座。

---

## 1. 唯一入口文件

- **防什么**：AI 每次进来都从零开始猜自己该干什么；不同 agent 各读各的规则，行为不一致。
- **什么时候要**：总是要。这是 L0 唯一必须有的东西。
- **最小做法**：根目录一个 `AGENTS.md`，写身份、目录结构、路由表、规则边界、优先级、每次对话的工作流、输出原则。写法见 `入口文件写法.md`。
- **多 agent**：内容只写在 `AGENTS.md` 一处。某个 agent 只认别的文件名时，放一个同名文件，里面只写一句"读 AGENTS.md"，或者用软链接，不维护第二份内容。动手前先确认当前 agent 实际读哪个文件名，不要凭印象。
- **常见坏法**：入口文件写成技能大全，几百行执行细节；入口和技能里各写一份同一条规则，后来只改了一边。

## 2. 身份与说话方式

- **防什么**：AI 用"助手腔"讨好用户，不指出问题；不同对话里语气忽冷忽热。
- **什么时候要**：AI 要给判断、建议、审查意见时要。纯执行型工作台（比如只整理文件）写一句就够。
- **最小做法**：入口文件开头写三样：你是谁（角色）、你怎么工作（读什么 → 分析什么 → 交付什么）、你怎么说话（对用户的态度、该不该直接指出问题、用户是什么水平）。
- **常见坏法**：只写形容词（"专业、友好、高效"），AI 照样不知道该怎么做。要写成能看出有没有做到的行为，比如"发现用户方案有问题，第一句就说"。

## 3. 服务对象档案 + 建档技能

- **防什么**：AI 给的都是对谁都成立的通用建议。
- **什么时候要**：工作台服务的是一个具体的人、团队、客户或产品，而且建议要随这个对象变。
- **什么时候不要**：服务对象每次都不同，并且不需要记住（比如一次性的文档格式转换）。
- **最小做法**：根目录一个档案文件（名字按领域取：角色卡、客户卡、产品卡……），只放长期有效的结论；一个建档技能负责首次采集和更新；入口文件规定"每次对话先读档案，档案不存在就触发建档"。
- **常见坏法**：档案越写越长，什么过程都往里塞。档案只放结论，过程放进度或记录文件。

## 4. 路由表

- **防什么**：用户说了一句话，AI 不知道该走哪个流程，或者凭感觉自己即兴发挥。
- **什么时候要**：有 2 个及以上技能或轻量指令时要。
- **最小做法**：入口文件里一张表，左边写"用户行为 / 用户原话的样子"，右边写去哪个技能、技能的哪个用法，或者"不走技能，直接 X"。技能内部有多种用法的，在技能里再放一张二级路由表。
- **常见坏法**：左边写成抽象分类（"写作类需求"），AI 对不上用户的原话；两行抢同一句话；有技能没有路由，或者路由指向不存在的技能。

## 5. 技能唯一源头

- **防什么**：同一个技能在几个 agent 目录里各有一份，改了一份忘了另一份。
- **什么时候要**：用两个及以上 agent，或者以后可能换 agent 时要。
- **最小做法**：技能只放在一个源头目录（默认 `.agents/skills/`）。其他 agent 读取技能的路径用软链接指向它，入口文件的目录结构里写清"哪个是源头，哪个是链接"。
- **常见坏法**：复制而不是链接；入口文件没写清楚，后来的人改错了地方。

## 6. 渐进读取

- **防什么**：每个任务都把整个知识库读一遍，上下文被占满，重点被淹没。
- **什么时候要**：技能附带的知识超过一两百行，或者不同用法要读不同的东西。
- **最小做法**：`SKILL.md` 只放分流、流程和"这次读哪几份"。细节拆到 `references/`（方法）、`knowledge/`（积累的知识）、`types/`（按类别分的写法）、`assets/`（素材、模板）里。`SKILL.md` 用一张表写"做什么任务 → 读哪些文件 → 然后做什么"。
- **常见坏法**：拆了文件，但 `SKILL.md` 写着"先读完 references 下所有文件"，拆了等于没拆。

## 7. 状态文件与写权限

- **防什么**：工作台没有记忆，每次从零开始；或者几个技能都去写同一个文件，内容互相覆盖、互相矛盾。
- **什么时候要**：工作需要积累（规律、候选、进度、历史决策）时要。这是 L2 的标志。
- **最小做法**：按状态的类型建文件（类型见 `状态与记忆.md`），然后在入口文件或各技能里明确**谁读、谁写、什么时候写**。一个文件原则上只有一个写入方；必须有多个写入方时，写清每一方各写哪一段。
- **常见坏法**：只有"读"的说明，没有"写"的规则；用户随口一句话被 AI 写成了"已验证规律"。

## 8. 产物三段式

- **防什么**：草稿、中间文件和定稿混在一起，找不到哪版是真的；AI 跑完一次流程就自作主张当成定稿。
- **什么时候要**：工作会产出文件时要。
- **最小做法**：
  - `raw/`：用户给的原始资料，只读，不放 AI 生成的东西。
  - `temp/<YYYY-MM-DD_任务名>/`：所有中间产物，包括下载、转写、分析、候选、草稿、预览。
  - `output/<YYYY-MM-DD_任务名>/`：只放用户明确确认的定稿。入口文件里写死**定稿触发语**（"定稿""就这版""正式输出"……），并写明哪些情况不算定稿（流程跑完、首次导出、生成预览）。
- **常见坏法**：没有定稿触发语，AI 每次都往 output 写；`raw/` 里混进了 AI 改过的版本，原件丢了。

## 9. 反馈闭环

- **防什么**：工作台的判断永远不会变准，错了也没人知道。
- **什么时候要**：工作结果能被观察到（数据、采纳与否、成败），并且用户愿意把结果带回来。这是 L3 的标志。
- **什么时候不要**：结果拿不到，或者要很久才出来，久到没人会回来复盘。这时先不建，蓝图里写明"以后拿到 X 数据再加"。
- **最小做法**：事前记录（判断写下来，写完不改）→ 结果回收 → 对照找原因 → 结论写回规律文件。详见 `反馈闭环.md`。
- **常见坏法**：事后改事前记录；一条结果就改规律；规律文件没区分"已验证"和"待验证"。

## 10. 可扩充入口

- **防什么**：每加一个新类别都要重写技能，或者 AI 遇到没见过的类别就硬套已有的类别。
- **什么时候要**：技能内部按类别走不同写法，并且类别会增加（文书类型、客户类型、内容类型……）。
- **最小做法**：每个类别一个文件（`types/<类别>.md`），外加一个 `_新分类模板.md`。`SKILL.md` 里放一张分类表，并写明：哪一类都不像时怎么办（先用通用规矩做，同时问用户要不要加一类）；用户说"加一个分类：X"时怎么做（复制模板 → 填 → 在分类表加一行）。模板见 `templates/扩充分类.md`。
- **常见坏法**：模板只有标题没有填写说明；新类别不要求写数据依据或判断依据，凭空编写法。

## 11. 边界与隔离

- **防什么**：AI 用外部账号做了写操作；读了不该读的凭据；把页面里的文字当指令执行；一个敏感话题的记忆混进了日常产出。
- **什么时候要**：接外部系统或数据、处理敏感信息、有话题需要和日常工作隔开时要。
- **最小做法**：入口文件里每条边界单独一段：范围、允许做什么、不允许做什么、失败了怎么办、为什么。模板见 `边界与安全.md`。
- **常见坏法**：只写"注意安全"；访问工具失败时 AI 偷偷换一条通道继续做；隔离只写了"不要用"，没写"存哪里、什么时候才读"。

## 12. 轻量指令

- **防什么**：为一件很小的事建一个技能，路由变复杂；或者小事没有规则，AI 每次自由发挥。
- **什么时候要**：有高频、一步就能做完、没有方法论的操作，比如"记一下 X""把这条加进清单"。
- **最小做法**：入口文件里单独一节"不用技能的几件事"，每件写清触发语、动作、写到哪、不做什么（比如"不追问、不改写"）。
- **常见坏法**：轻量指令越写越长，长出了流程和判断，这时它已经该升级成技能了。

## 13. 优先级

- **防什么**：入口文件、技能和用户当场的要求互相矛盾时，AI 不知道听谁的。
- **什么时候要**：总是要，写一小节就够。
- **最小做法**：用户当前明确要求 > 对应技能的 `SKILL.md` > 入口文件。再补一句：技能管执行细节，入口只管入口和边界。有专项约定（隔离、数据访问）比技能更优先的，单独写明。

## 14. 演化记录

- **防什么**：规则改了没留痕，过几个月没人知道为什么这么写；用户纠正过的地方又被改回去。
- **什么时候要**：工作台会长期用、规则会随实践调整时要。
- **最小做法**：
  - 改规则时就地写一句"YYYY-MM-DD 改：原因"，旧做法彻底作废的要写明"作废"。
  - 用户明确纠正 AI 的地方，直接改，并写日期。
  - 知识库、分类文件末尾放"维护记录"。
  - 引用外部方法论的，写出处，并写改了什么。
- **常见坏法**：只改不记；或者反过来，把改动日志写得比规则本身还长。超过 5 条的历史可以挪到单独的 `CHANGELOG.md`。
