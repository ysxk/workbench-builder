# 资料提炼：把课程、文档、转录稿变成技能

用户丢来一堆课程讲义、文章、视频转录稿，说"把这个做成技能"。这时要做的不是摘抄，而是**提炼**：把讲的人脑子里那套判断方法抽出来，写成给 AI 看的指导。

## 核心认识

- 课程是讲的人**在某一个场景里的一次演示**：他的案例、他的账号、他当时的平台、他那天想到的例子。
- 技能是让 AI **在没见过的场景里也能做对**的指导。
- 所以要提的是"为什么这么做、什么情况下这么做、怎么判断做对了"，不是"他说了哪句话"。只照着原句写，技能只能解决和课程一模一样的那道题。

## 三层内容

读资料时，把每段话归进三层中的一层：

| 层 | 是什么 | 去哪 |
|---|---|---|
| **理念** | 讲的人想解决的根本问题；他在优化什么、警惕什么 | 技能 `SKILL.md` 的开头和原则 |
| **方法** | 能迁移的步骤、判断标准、取舍规则、常见失败 | 技能 `SKILL.md` 的流程，细节放 `references/` |
| **实例** | 他的案例、原话、数字、平台细节、个人经历 | 不进技能。最多挑 1–2 个当"示意"放进 `references/`，标明"示意，换个场景要重新推" |

用户本人的情况（他的数据、作品、偏好、过往案例）不属于这三层，它们**属于知识库和记忆**，见下面「技能和知识库的分工」。

## 提炼流程

### 1. 盘点

- 列出所有资料：标题、类型（讲义 / 转录 / 文章 / 笔记）、长度、主题。
- 原件存进工作台的 `raw/`。清洗稿（去掉口头禅、修正明显的转写错误）放 `temp/<YYYY-MM-DD_提炼-主题>/`。
- 转录稿里拿不准的专有名词（人名、工具名、术语）列出来问用户，不要猜。
- 资料很长时分批读。每批写完意图笔记（第 2 步）再读下一批，不要一次全读完再凭印象总结。

### 2. 逐段读意图

每读完一段，对自己问四个问题，写成意图笔记：

1. 他在解决什么问题？（不是"他说了什么"）
2. 他为什么认为这样做有效？背后的道理是什么？
3. 换一个领域、换一个人、换一个平台，这条还成立吗？在什么条件下会失效？
4. 他反复强调、或者明确反对的是什么？

意图笔记格式：

```
- [理念 / 方法 / 实例] 一句话写意图 —— 依据：<资料名 + 位置>
```

依据必须能回溯到资料里的具体位置，但笔记里不抄原文长段。

### 3. 合并

- 把所有资料的意图笔记放在一起，同一个意思的合并成一条，并记下出现了几次。
- 在多份资料、多个场景里反复出现的，才是核心理念；只出现一次的，先当方法或技巧。
- 几份资料互相矛盾的：写出矛盾，找出各自成立的条件，写成"在 A 情况下这样做，在 B 情况下那样做"。找不出条件的，问用户站哪边。

### 4. 抽象，但抽到能执行为止

把每条方法从"这一句"提升到"这一类"，但不要提升成空话。

| 太具体（只能解决当下） | 合适（能迁移、能执行） | 太抽象（空话） |
|---|---|---|
| 客户说"太贵了"，就回"您是和哪家比的" | 碰到异议，先问清它背后在和什么比较，再给方案。适用：价格能谈的一对一销售。不适用：价格公开、统一定价 | 要理解客户需求 |
| 标题里写"3 个方法" | 标题里给出具体的、可数的承诺，让读者知道读完能拿走什么 | 标题要吸引人 |
| 第一句就说"我做了 10 年会计" | 开场先让对方知道你凭什么值得听，用能被核实的事实，不用形容词 | 要建立信任 |

判断标准，两条都要满足：

- **能迁移**：拿一个课程里没出现的场景，这条规则还能告诉 AI 该怎么做。
- **能执行、能检查**：AI 知道具体该做什么动作，事后能看出有没有做到。

每条规则写成："**在什么情况下 → 做什么 → 为什么 → 什么时候不适用**"。"为什么"一定要写，AI 知道原因，遇到规则没覆盖的情况才推得出来。

### 5. 剥离讲的人的特殊条件

讲的人的结论往往建立在他自己的条件上：粉丝量、行业、预算、平台当时的规则、他本人的风格。

- 他的**数字阈值**（"回复率到 15% 就算合格""每周发 3 次"）不能直接写成规则。改成"用本人自己的数据定基线"，并指向知识库里放数据的位置。
- **平台或工具的现状**（某个功能、某个算法说法）会过时，写成"截至资料时间的说法，用前先核实"，或者干脆不写。
- 他的**个人风格**（口头禅、标志性句式）不是方法。除非用户想学的就是这种风格，否则不进技能。

### 6. 分去处

| 内容 | 去处 |
|---|---|
| 核心理念、流程、判断标准、输出格式 | `SKILL.md` |
| 方法细节、概念定义、分类写法、少量示意案例 | 技能的 `references/` 或 `types/` |
| 用户自己的情况、数据、作品、偏好 | 档案、知识库、状态文件（技能里只写"去哪里读，读不到怎么办"） |
| 课程里的案例原文、原话 | 不保留，或只作为依据，指回 `raw/` 里的原件 |
| 闲聊、广告、和主题无关的内容 | 丢掉 |

### 7. 定技能边界

按 `技能拆分判断.md` 拆。**课程的章节结构不等于技能结构**：一门课的五章可能只是一个技能的五个步骤，也可能是三个互不相干的技能。按用户会怎么用来拆（他会说什么话来触发），不按课程目录来拆。

### 8. 出提炼报告，停下等确认

落盘前先给用户看：

```
## 提炼报告：<资料主题>
资料：<N 份，总长约 X 字 / X 分钟>

### 核心理念（3–7 条）
1. <一句话> —— 出现在 <资料 A、C、D>

### 拟建技能
| 技能 | 解决什么 | 主要的方法 | 读哪些用户数据 |

### 去知识库 / 记忆的
- <哪些内容需要沉淀成用户自己的数据，现在有没有，没有的话以后由谁写>

### 没收进来的
- <实例、过时内容、讲的人的个人条件> —— 理由

### 有矛盾或需要你定的
- …
```

用户确认后才写技能文件。写法按 `技能写法.md`；外部课程要在技能开头写出处和许可证，并写明"按本工作台改了什么"。

### 9. 迁移测试

技能写完后，编 3 个**课程里没出现过**的任务，只给 AI 这份技能（不给原始资料），看它能不能做对：

- 能做对：通过。
- 做不出来，或者只能照搬课程里的例子：说明抽象得不够，或者"为什么"没写清楚，回到第 4 步。
- 做出来的东西空泛：说明抽象过头了，补上执行动作和判断标准。

## 技能和知识库的分工

这是整个工作台都要守的分工，不只适用于提炼：

| | 技能（`SKILL.md`、`references/`） | 知识库与记忆（技能的 `knowledge/`、档案、状态文件） |
|---|---|---|
| 写的是 | 怎么做：理念、方法、判断标准、流程 | 对谁做：这个人的情况、数据、作品、偏好、验证过的规律 |
| 什么时候变 | 方法本身被证明不对时才改 | 随使用不断积累 |
| 从哪来 | 方法论、课程、经验的抽象 | 建档、复盘、用户纠正、用户的历史产出 |

**换人测试**：把这个技能整个交给另一个用户用，`SKILL.md` 和 `references/` 应该一个字都不用改，只有 `knowledge/` 和状态文件需要重建。要改的地方，说明用户的特殊情况混进了技能，把它挪到知识库，技能里只留"去哪读"。
