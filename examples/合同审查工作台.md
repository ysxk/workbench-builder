# 示例：合同审查工作台（L2，虚构）

> 演示一个以文本审查为主、结果很难量化的工作台长什么样。条目都是虚构的，不要搬进真实工作台。

## 访谈结论

- 领域：中小企业的合同审查
- 服务对象：一位独立执业律师，常年服务 6 家企业客户。每家的行业、风险偏好、常用的合同版本都不一样
- 反复做的工作：
  1. 审合同（每周 5–8 份）：现在逐条读，最常漏的是付款条件和违约金的上限
  2. 改合同（每周 2–3 份）：按客户立场出修订稿，最费时的是把同样的修改意见反复重写
  3. 记一个条款问题（随时）：发现一个好写法或一个坑，想先记下来
- 输入来源：用户上传 Word / PDF；没有外部系统
- 产出与定稿：审查意见表、修订稿。律师说"发给客户""定稿"才算定稿
- 做好的标准：律师采纳了多少条意见，客户后来有没有因为某个条款出事。结果要几个月才出来，而且只有部分能知道
- 红线：A 客户的合同内容绝不能出现在 B 客户的产出里；AI 不直接对外发任何东西
- 需要隔离的话题：无（按客户分目录已经能隔开）
- 环境：两个 agent 共用
- 未知项：各客户的风险偏好，先按"中性"处理，建档时补
- 建议成熟度：**L2**。审查需要积累条款知识和客户偏好；客户结果太慢，反馈闭环先不做，只记"意见被采纳了没有"

## 拆工作

| 工作 | A 频率 | B 固定做法 | C 要知识 | 归宿 |
|---|---|---|---|---|
| 审合同 | 是 | 是 | 是（条款库 + 客户偏好） | 技能 `contract-review` 的"审查"用法 |
| 改合同 | 是 | 是 | 同上 | 同一个技能的"修订"用法：和审查读的是同一批文件 |
| 积累条款写法 | 持续 | 是 | — | 知识库型技能 `clause-library` |
| 记一个条款问题 | 高 | 否 | 否 | 轻量指令 |
| 新客户建卡 | 偶尔 | 是 | — | 建档技能 `client-onboarding` |

## 目录树

```
contract-desk/
├── AGENTS.md
├── clients/
│   ├── README.md                ← 一家客户一个目录；不跨目录引用
│   └── <客户代号>/
│       ├── profile.md           ← 客户卡：行业、立场、风险偏好、常用版本
│       ├── reviews/             ← 审查记录：每份合同的意见表，以及哪些被采纳
│       └── raw/                 ← 客户给的原件
├── 条款问题池.md                 ← 随手记的条款问题，等着整理进条款库
├── temp/
├── output/<客户代号>/<YYYY-MM-DD_合同名>/
└── .agents/skills/
    ├── client-onboarding/
    ├── contract-review/
    │   ├── SKILL.md
    │   └── types/               ← 买卖、服务、租赁…… 加 _新分类模板.md
    └── clause-library/
        ├── SKILL.md
        └── knowledge/           ← 付款.md、违约.md、知识产权.md…… 每条写好写法和坑
```

和单人工作台的区别：档案按客户分目录，因为红线是客户之间不能串。

## 路由表

| 用户说 | 去哪 |
|---|---|
| "新客户""给 X 建个卡" | `client-onboarding` |
| "帮我看看这份合同""这条有没有坑" | `contract-review` 审查 |
| "按甲方立场改一版""出修订稿" | `contract-review` 修订 |
| "这条款一般怎么写""付款条款有哪些坑" | `clause-library` |
| "记一下：X" | 原话加进 `条款问题池.md` 最上面 |
| "这份合同"但没说是哪家客户 | 先问是哪家客户，不猜 |

## 写权限表

| 文件 | 谁读 | 谁写 | 什么时候写 |
|---|---|---|---|
| `clients/<代号>/profile.md` | 审查、修订 | `client-onboarding` | 建卡、用户说"更新 X 的偏好" |
| `clients/<代号>/reviews/` | 审查 | `contract-review` | 每次审完写意见表；律师反馈后追加"采纳 / 未采纳" |
| `clause-library/knowledge/` | 审查、修订 | `clause-library` 的整理用法 | 用户说"把池子里的整理进条款库" |
| `条款问题池.md` | `clause-library` | 轻量指令 | 用户说"记一下" |

## `contract-review` 的 SKILL.md 要点

- 先读：客户卡 → 对应合同类型的 `types/<类型>.md` → `clause-library` 里相关的条款文件
- 审查输出格式（填好的示例）：

```
| # | 条款 | 风险 | 等级 | 建议改法 | 依据 |
| 1 | 第 5.2 条 付款 | 验收后 90 天付款，没写逾期利息 | 高 | 改为 30 天，加逾期利息 | 条款库/付款.md#账期 |
```

- 每条意见都要有依据：条款库里的条目，或者客户卡里的偏好。没依据的标"经验判断，待确认"
- 律师反馈后，在意见表里追加采纳情况。同一类意见连续 3 次未被采纳，就提示"要不要更新客户偏好"。这是 L2 版的轻量反馈，不预测，只记录

## 边界

- 客户隔离：处理 A 客户时只读 `clients/A/`；产出里不出现其他客户的名称、金额、条款原文
- 定稿：律师说"发给客户""定稿"才复制进 output
- 不对外发送任何东西，只准备好文件

## 路由测试（节选）

| 用户说 | 应该去 | 结果 |
|---|---|---|
| "看下这份合同" | 先问是哪家客户 | ✅ |
| "这条违约金高不高" | `contract-review` 审查（单条） | ✅ |
| "违约金一般定多少" | `clause-library` | ✅ 和上一句靠"有没有具体合同"区分 |
| "帮我起诉对方" | 工作台不接，直接说明 | ✅ |

## 这次不做

- 反馈闭环：客户出不出事要几个月才知道，等积累了 20 份以上的意见采纳记录再评估
- 外部数据接入：没有需要接的系统
