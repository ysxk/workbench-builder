# 示例：独立开发者产品运营工作台（L3，虚构）

> 演示一个有结果数据、能做反馈闭环的工作台长什么样。条目都是虚构的，不要搬进真实工作台。

## 访谈结论

- 领域：独立开发者给自己的一款付费工具 App 做运营
- 服务对象：开发者本人 + 这款产品。产品的定价、用户群、渠道是长期信息
- 反复做的工作：
  1. 每次发版前，判断这版改动（新功能、改定价、改商店页）对转化有没有用：每 2 周一次，现在全凭感觉
  2. 发版后复盘：经常忘
  3. 处理用户反馈，决定下一版做什么：每天都有，反馈散在邮件和评论里
  4. 写更新日志和商店文案：每版一次
- 输入来源：应用商店后台导出的 CSV、网站统计的导出数据、用户把反馈粘贴进来
- 产出与定稿：发版判断、复盘记录、需求排序、更新文案。文案要开发者说"就这版"才算定稿
- 做好的标准：发版后 7 天的试用转付费率、商店页转化率。每次发版都能拿到
- 红线：不碰后台登录凭据；不替用户回复评论
- 需要隔离的话题：在谈的一笔收购，只在用户提到时读
- 环境：一个 agent
- 建议成熟度：**L3**。每 2 周一次发版，7 天就有结果，闭环转得起来

## 拆工作

| 工作 | 归宿 | 理由 |
|---|---|---|
| 发版前判断 + 发版后复盘 | 技能 `release-bet` 的两种用法 | 读同一批数据，事前和事后是一个闭环 |
| 反馈整理和需求排序 | 技能 `feedback-triage` | 每天都做，有固定的打标签方法 |
| 更新日志 / 商店文案 | 技能 `release-copy` | 每版一次，要读产品卡和过往文案 |
| 记一个需求 | 轻量指令 | 原话进需求池 |
| 读商店后台数据 | 先不做工具型技能 | 用户自己导出 CSV 就够，省得处理登录 |

## 目录树

```
app-ops/
├── AGENTS.md
├── product.md                  ← 产品卡：定位、定价、用户群、渠道
├── 规律.md                     ← 哪类改动对转化有用：已验证 / 待验证 / 预测准不准
├── 需求池.md                    ← 没做 / 在做 / 做过
├── data/
│   ├── README.md               ← 只放用户导出的原始 CSV，文件名带导出日期
│   └── raw/
├── bets/                       ← 发版判断：一版一个文件，写完不改，复盘追加在后面
├── deals/acquisition/          ← 隔离：memory.md + raw/
├── temp/
├── output/
└── .agents/skills/
    ├── onboarding/
    ├── release-bet/
    ├── feedback-triage/
    │   └── references/标签体系.md
    └── release-copy/
```

和合同审查工作台的区别：只服务一个对象，所以没有对象子目录；多了 `规律.md` 和 `bets/` 这条闭环。

## 路由表

| 用户说 | 去哪 |
|---|---|
| "这版值不值得发""改价会怎样" | `release-bet` 发版判断 |
| "上一版数据出来了""复盘" | `release-bet` 复盘 |
| "这些反馈帮我理一下""下一版做什么" | `feedback-triage`（要的是文案，走 `release-copy`） |
| "写个更新日志""改下商店描述" | `release-copy` |
| "记个需求：X" | 原话加进 `需求池.md` 最上面 |
| 提到收购、"那笔交易" | 读 `deals/acquisition/memory.md` |

## 写权限表

| 文件 | 谁写 | 什么时候写 |
|---|---|---|
| `product.md` | onboarding | 建档、用户说"产品信息变了" |
| `bets/<版本>.md` | `release-bet` | 发版前写判断，写完不改；复盘只在后面追加 |
| `规律.md` | `release-bet` 复盘 | 每次复盘后追加；够条件才改"已验证" |
| `需求池.md` | 轻量指令写"没做"；`feedback-triage` 改状态 | 分段写，各写各的 |
| `deals/acquisition/` | 只在用户谈这个话题时写 | — |

## `release-bet` 闭环

- 事前：`bets/v2.3.md`。"试用转付费率 7 天内从 4.1% 到 4.5–5.5%。对照：v1.8 改付费墙文案 +0.6pt，v2.0 加年付选项 +1.1pt。"
- 复盘：7 天后用户粘贴 CSV。追加实际值、来源"商店后台导出 CSV，YYYY-MM-DD 导出"，并写原因
- 写回：一次只写"待验证"；同方向满 3 次才升"已验证"
- 不用打分模型：等 `规律.md` 里的"预测准不准"攒到 10 条，再评估要不要用

## 边界

- 数据只用用户导出的文件，不登录后台，不读凭据
- 评论回复只出草稿，由用户自己发
- 收购话题：按 `references/边界与安全.md` 的隔离模板写。写日常文案时不读、不引用

## 路由测试（节选）

| 用户说 | 应该去 | 结果 |
|---|---|---|
| "数据出来了" | `release-bet` 复盘（找最近一个没复盘的 bet） | ✅ |
| "用户说太贵了，要不要降价" | `release-bet` 判断：降价是一次发版改动 | ✅ |
| "把这几条用户反馈写成更新日志" | `release-copy`，素材来自反馈 | ⚠️ 第一次测试时和 `feedback-triage` 抢 → 已在路由表加"要的是文案，走 release-copy"，重测 ✅ |
