# workbench-builder：搭建工作台

一个教 AI 搭建"文件即系统"工作台的技能。

**文件即系统的工作台**没有页面、没有程序，只有几样东西：

- 一个入口规则文件（`AGENTS.md`）
- 一组技能（每个技能教 AI 做一件事）
- 若干状态文件（档案、规律、候选池、记录）
- 产物目录（原始 → 中间 → 定稿）

有了这些，AI 每次进来都知道自己是谁、该做什么、该读写哪里，并且越用越懂服务对象、越用越准。它本质上是一套写给 AI 的"岗位手册 + 工作记忆"。

## 能做什么

| 用法 | 你可以这样说 | 它会做什么 |
|---|---|---|
| 新建 | "帮我搭一个合同审查工作台""把我做 X 的经验变成工作台" | 访谈 → 拆工作 → 出蓝图等你确认 → 建文件 → 自检 |
| 体检 | "看看我这个工作台哪里有问题" | 按检查清单诊断，先给出最该修的 1–3 个问题 |
| 扩建 | "给工作台加一个技能""加一个分类" | 出小蓝图，更新路由表和写权限表，检查和已有技能有没有冲突 |
| 资料提炼 | "把这些课程 / 文档 / 转录稿拆成技能" | 读意图、抽象出理念和方法，写成能迁移的技能，不摘抄原句 |
| 揣摩 | "参照这个工作台，给 Y 领域搭一个" | 只学结构，不搬内容；从访谈重新推导 |

## 设计原则

1. **结构可以借，内容不能搬。** 参照别的工作台时，只学"它用什么结构防住了什么问题"。
2. **按需加层。** 分 L0–L3 四级成熟度，默认只建到 L1 或 L2；能拿到结果数据了，再加反馈闭环。
3. **先蓝图，后落盘。** 用户确认之前不建文件。
4. **一件事只有一个地方说了算。** 入口文件管入口和边界，技能管执行细节。
5. **技能只写方法，用户的特殊情况沉淀进知识库。** 换一个用户用，技能本身一个字都不用改。

## 安装

把这个仓库放进你的 agent 读取技能的目录。下面以 `~/.agents/skills/` 作为唯一源头，其他 agent 的技能目录用软链接指过去：

```bash
git clone https://github.com/ysxk/workbench-builder.git ~/.agents/skills/workbench-builder

# Claude Code
ln -s ~/.agents/skills/workbench-builder ~/.claude/skills/workbench-builder
```

不同 agent 读取技能的路径不一样，以它们各自的文档为准。只要那个目录里能读到 `SKILL.md` 就行。

## 目录

```
workbench-builder/
├── SKILL.md                 ← 入口：五条底线、成熟度分级、用法分流、各用法流程
├── references/              ← 方法文档，按需读取
│   ├── 访谈清单.md           ← 新建时要问清楚的 7 组问题
│   ├── 技能拆分判断.md       ← 什么该做成技能，什么只要一条规则
│   ├── 架构模式.md           ← 14 种常用结构：防什么、什么时候要、怎么做
│   ├── 入口文件写法.md
│   ├── 技能写法.md
│   ├── 状态与记忆.md         ← 7 类状态和写权限表
│   ├── 反馈闭环.md           ← 事前记录 → 结果回收 → 规律写回
│   ├── 边界与安全.md         ← 定稿、外部数据、隔离记忆、敏感信息
│   ├── 资料提炼.md           ← 把课程、文档、转录稿抽象成技能
│   └── 检查清单.md           ← 路由测试、引用、写权限、残留、空话、抽象检查
├── templates/               ← 带占位符的空骨架
│   ├── 入口文件.md
│   ├── 档案.md
│   ├── 技能-建档.md / 技能-流程型.md / 技能-知识库型.md / 技能-工具型.md
│   └── 扩充分类.md
└── examples/                ← 两个虚构的示例，演示结构怎么随领域变形
    ├── 合同审查工作台.md      ← L2，按客户隔离，不做反馈闭环
    └── 独立开发者产品运营工作台.md ← L3，有数据回收和反馈闭环
```
